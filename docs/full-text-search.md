# Rehearse search behavior after a migration

A migration can preserve article rows while removing the trigger that updates
their search index. A consistent index can also return different results after
a tokenizer change. Declare the writes and search queries your application
depends on, then compare them on disposable before/after copies.

SchemaRehearsal 0.4.0 supports SQLite's built-in FTS5 with explicit opt-in.
FTS5 is SQLite's full-text search module. Its availability depends on your
Python SQLite build. No extension is downloaded or loaded. Other virtual-table
modules remain unsupported, and virtual tables are still refused by default.

## Run the complete example

For a first look without installation, run this from the source checkout:

```sh
python3 examples/quickstart.py --fts5 search-demo
```

Open `search-demo/broken/report.html`. The script checks the expected lost-search
result and the repaired and unchanged controls, then exits 0 only when all three
results reproduce. It creates only synthetic data in a new directory and needs
Python 3.11+ with built-in SQLite FTS5. General integrity checks in these reports
are not the full FTS5 index/content consistency check described below.

Install the release wheel or source checkout. From a release source archive or
checkout, choose a new destination whose parent exists:

```sh
python examples/full_text_search.py /tmp/schema-search-demo
```

This runs the production CLI, including its default refusal. It creates three
original synthetic articles with nonconsecutive rowids, an external-content
index and insert/update/delete triggers. It checks:

| Migration | Declared result | Exit |
| --- | --- | --- |
| Drop the update trigger | An updated article disappears from search; insert/delete scenarios still match | 1 |
| Recreate the update trigger | All three write/search workflows match | 0 |
| Replace the Porter stemmer with `unicode61` | The declared stemmed search changes | 1 |
| No-op → drop trigger → restore trigger | `matched → changed → matched`; first change 2, final matched | 1 |

The script checks the controlled source file's bytes and that report JSON omits
search terms, article text, SQL and the source path. These are synthetic examples,
not production failures or evidence of outside use.

Open `/tmp/schema-search-demo/broken/report.html`. The updated-article observation
has one result before migration and zero after. Insert/delete scenarios start
from fresh copies. The [sample report](search-example.html) is generated by this
same recipe.

## Use the CLI directly

```sh
schema-rehearsal example --fts5 search-example
schema-rehearsal check --allow-fts5 \
  --database search-example/articles.sqlite \
  --migration search-example/broken.sql \
  --suite search-example/suite.json --output search-report
# Exit 1: the update/search behavior changed.
```

Use `--allow-fts5` for `sequence` too. In Python, pass `allow_fts5=True` to
`rehearse()` or `rehearse_sequence()`. The flag permits FTS5 table creation and
removal in migrations and the internal SQLite operations needed for FTS5.
Scenario steps remain data mutations; observations remain read-only. Attachment,
external extensions, explicit TEMP objects and unsafe pragmas stay blocked.
Existing size, result and time limits still apply.

Write deterministic observations, for example a parameterized `MATCH` query
returning rowids with `ORDER BY rowid`. Use `bm25()` and ranking only with an
explicit stable tie-breaker. Result values stay private in memory; names, row
counts, schema names and hashes remain visible in reports. Do not put search
terms or private article text in descriptive names.

## Compare against SQLite's own checks

SQLite already provides [FTS5 integrity-check](https://www.sqlite.org/fts5.html#the_integrity_check_command).
For an external-content table, `rank=1` checks the index against its content.
On your own disposable copy, the example's full check is:

```sql
INSERT INTO search(search, rank) VALUES('integrity-check', 1);
```

Testing writes followed by this built-in check is a useful conventional way to
catch synchronization failures. A check before any write cannot establish
whether future writes maintain the index. A consistent index also does not
specify whether your application's query should still find the same articles
after changing tokenization.

SchemaRehearsal does not automatically run this FTS5 command. Its reported
`integrity_ok` and `foreign_keys_ok` fields refer to the general database checks,
not index-to-content consistency. Include application search observations in
your suite and use the built-in full check separately when that is your goal.
An unexpected SQLite execution error is reported as an error, with raw details
omitted; it is not silently treated as an empty search result.

Migration tests and SQL assertions are established techniques. A small disposable
SQL test may be simpler for a single query. This extension lets an existing
SchemaRehearsal suite retain its independent scenarios, checkpoint comparisons
and private-value reports when the database contains FTS5. It does not certify
every write path, undeclared search query, tokenizer, ranking rule or future
SQLite version.
